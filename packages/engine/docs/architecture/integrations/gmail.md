# Gmail Integration

Gmail is a Google-provider OAuth service (`packages/tools/src/services/google/gmail.ts`). Its tools call the Gmail REST API directly with raw `fetch` (no `googleapis` SDK), authenticated by the credential the dispatch layer resolves and injects; an executor never resolves a credential itself.

The tool surface landed in three tiers by rising consequence: read + search (Tier 1, no new scope), send + reply (Tier 2, adds `gmail.send`), draft + mailbox hygiene (Tier 3, adds `gmail.modify`). All three tiers are on `main`.

## Tool surface

Each tool is its own `(service, verb)` permission subject with its own noun. The noun is extracted synchronously from the call's own params — no credential, no network — so it is the grant key and the audit target at once.

| Tool | Verb | Noun | Capability |
|------|------|------|-----------|
| `gmail_list` | `list` | the mailbox label listed (`INBOX`, `SENT`, …) | read |
| `gmail_read` | `read` | the constant sentinel `mailbox` — read is consented per account/session, not per message; the message id's value is not audited — the row records only the parameter's shape | read |
| `gmail_search` | `search` | the mailbox/label the query resolves to (`in:sent` → `SENT`; `in:drafts` → `DRAFT`; a user label → `label:<name>`; unfiltered or `in:anywhere` → `anywhere`); the raw `q` is never the noun, and its value is not audited — the row records only its shape | read |
| `gmail_send` | `send` | the set of distinct recipient addresses across `to`+`cc`+`bcc`, lower-cased, de-duped, sorted, comma-joined; an unparseable address contributes an opaque `unparseable:<raw>` token, never dropped | send |
| `gmail_reply` | `reply` | `send`'s recipient-address noun *shape*, over the reply's own params — `threadId`/`inReplyTo` set threading only and never enter the recipient set | send |
| `gmail_draft` | `draft` | `send`'s recipient-address noun *shape* — a draft names recipients even though it sends nothing | draft |
| `gmail_archive` | `archive` | the constant `INBOX` — archive is defined as removing INBOX | modify-labels |
| `gmail_mark_read` | `mark_read` | the constant `UNREAD` | modify-labels |
| `gmail_label` | `label` | the set of labels being mutated (added + removed), canonicalized to label ids (`starred` → `STARRED`, `Label_<n>` verbatim, an unresolvable display name → `label:<name>`), sorted, comma-joined; `TRASH`/`SPAM` are refused (use `gmail_trash`) | modify-labels |
| `gmail_trash` | `trash` | the constant `TRASH`; permanent delete is deliberately not exposed | trash |

A query whose narrowing the resolver cannot prove also nouns as `anywhere`: Gmail's disjunction syntax (`OR`, any case, or `{}` grouping) lets `in:sent OR from:x` read the whole account, and a quoted mailbox value (`in:"sent"`) resolves at Gmail after unquoting, which the whitespace tokenizer cannot see. Over-claiming to `anywhere` forces the widest consent; a narrow grant never covers a wider search. Negation (`-in:spam`) only narrows and passes through.

The `read` sentinel is deliberately not `*` (it survives wildcard-allow hardening), and label nouns are uppercase system IDs, `Label_<n>` ids, or `label:`-prefixed tokens, so no mailbox noun can collide with it.

Send and reply are consequential verbs: with no seeded grant they hold for confirmation on first use, and because the noun is the *whole* recipient-address set, any change to the recipients — an extra address, or a new mailbox even inside an already-granted domain — changes the noun and forces a fresh confirmation. A grant covers exactly the confirmed address set for the session; per-address subset coverage (a subset send riding existing grants) is planned follow-up work.

The hygiene tools mutate labels by **id**, not display name, and Gmail's modify endpoint rejects a display name. The fixed-target tools (`gmail_archive`, `gmail_mark_read`) hard-code the system id they touch, so they always work. `gmail_label` is reliable for the system labels an agent already knows (`STARRED`, `IMPORTANT`, `INBOX`, `UNREAD`) but not for arbitrary user labels: no read/search/list tool surfaces a message's `Label_<n>` ids today, so an agent cannot discover a user label's id to pass it. The noun recognizes Gmail's full system-id set — including the category (`CATEGORY_*`) and `CHAT` ids — and emits the real id for any of them, so a valid system label is never recorded as a `label:<name>` user label. Only an unrecognized value canonicalizes to the `label:<name>` token; a genuine display name then fails closed at Gmail (a 4xx surfaced as a tool error), never a wrong-label mutation, because the executor forwards the raw value and Gmail rejects it. `gmail_label` also refuses the `TRASH` and `SPAM` system labels outright — an input error before any request. Trashing is its own verb (`gmail_trash`) and marking spam is not exposed at all, so neither destructive move collapses into the low-consequence `label` grant. Surfacing `Label_<n>` ids on read (so an agent can target a user label) is a candidate follow-up; no issue yet.

## OAuth scopes and the capability check

`gmail.connect.scopes` requests `gmail.readonly` + `gmail.send` + `gmail.modify` (full `https://www.googleapis.com/auth/…` URLs) — the least-privilege non-redundant set for the full tool surface. `gmail.compose` is never requested: `modify` already authorizes drafts, and Google's consent screen and verification review both penalise requesting a scope another already implies. Note `gmail.modify` is a near-master scope (it authorizes read, draft, send, label, and trash — everything but permanent delete), so the blast-radius bound rests on governance (noun binding + confirmation holds), not scope narrowness.

Gmail's scopes are overlapping supersets — `gmail.modify` authorizes read, draft, send, label, and trash; `gmail.compose` authorizes draft and send; the umbrella `https://mail.google.com/` authorizes everything — so each tool declares a **capability** (`Tool.requiredScopes`): the set of scopes any one of which covers it (`GMAIL_CAPABILITY_SCOPES`). Every capability's set includes the umbrella scope: Habenula never requests it, but a credential is judged by what it holds, and the broadest grant must not read as a gap. The pre-policy scope precondition checks capability coverage against the credential's *actually granted* scopes, never exact-string membership: a `gmail.modify` credential satisfies `read` even with `gmail.readonly` declined, and a declined `gmail.send` fails closed to needs-authorization rather than reaching Gmail for a 403. A miss produces the `needs_authorization` outcome (see `docs/architecture/governance.md`), routing the user to re-connect out of band (`habenula connect gmail`).

**Per-service re-consent.** A Google consent returns a credential scoped to exactly the requested set — the begin-flow does not send `include_granted_scopes`, so connecting a second Google service (e.g. `google_calendar`) never widens Gmail's stored token, and vice versa. Re-consent still widens within Gmail because every connect requests Gmail's complete scope set: a user connected under the old readonly-only set keeps working for read tools, hits needs-authorization the first time an agent tries `gmail_send`, and re-connecting grants the full current set. The complete-scope-set invariant this rests on is recorded in [`footguns.md`](../../footguns.md).

**Acquiring the credential.** Registering the Google OAuth client and wiring its client ID/secret into Habenula is covered in [`connect/google.md`](../../connect/google.md).

## API quirks

- **List and search are N+1 fanouts.** `messages.list` / `messages.list?q=` return only ids; one `format=metadata` subrequest per id follows, in parallel. The fanout is bounded by the validated `maxResults` (shared ceiling in `services/shared/email.ts`), which spends the Worker subrequest budget, not just Gmail quota.
- **Bodies are base64url.** `gmail_read` fetches `format=full` and walks the (possibly nested) multipart payload: text/plain preferred, text/html fallback, decoded from base64url. The decoded body is capped at `GMAIL_READ_BODY_MAX_CHARS` (25k characters) with an explicit truncation marker — `format=full` has no server-side bound, and the body flows into the LLM context.
- **Bodies decode as UTF-8 only.** The decoder does not honor a part's `charset=` parameter; a non-UTF-8 message (e.g. ISO-8859-1) decodes with replacement characters. Known limitation, acceptable for Tier 1.
- **Label ids differ from display names.** The vocabulary label `DRAFTS` maps to Gmail's singular `DRAFT` label id; search nouns emit label IDs for system labels (`in:drafts` → `DRAFT`) and cannot resolve user labels to `Label_<n>` without a network call (hence the `label:<name>` token).
- **Send is a `raw` RFC 2822 message.** `messages/send` takes a base64url-encoded RFC 2822 payload; a reply is the same endpoint with `threadId` in the body and `In-Reply-To`/`References` headers. A `Bcc` header in the raw message is honored and stripped by Gmail. Every value interpolated into a header line — recipient addresses and the reply's `inReplyTo` Message-ID — has CR/LF folded to a space before assembly, so nothing can break out of its header and forge one (e.g. an injected `Bcc:`). This matters most for `inReplyTo`, which sets threading only and is never part of the recipient-domain noun: without the sanitizer a governed reply could still smuggle a header.
- **Header encoding.** A non-ASCII `Subject`, or a non-ASCII display name in `To`/`Cc`/`Bcc` (`Résumé <a@x.com>`), is RFC 2047 encoded-word wrapped so the header stays 7-bit ASCII; the addr-spec itself is left verbatim. A recipient list is split on commas *outside* double quotes, so a quoted display name that contains a comma (`"Last, First" <a@x>`) stays one recipient in both the governed noun and the `To` line. Two known Tier-2 limitations, both tolerated by Gmail: a very long non-ASCII value is emitted as one encoded-word rather than folded across the RFC 2047 length limit, and a reply's `References` header carries only the single answered Message-ID rather than the thread's accumulated chain (Gmail threads server-side on `threadId`).
- **Gmail's account send cap is independent of API quota.** Roughly 500 messages/day for consumer accounts, 2,000/day for Workspace — the only volume ceiling on a granted send until per-verb rate adverbs land.
- **Message bodies never enter the audit log.** `read`/`search` return bodies to the model (their purpose); the audit entry records parameter metadata only (metadata-only default, unchanged). Send/reply recipient addresses persist as the governed noun on the audit row; bodies are not recorded.
