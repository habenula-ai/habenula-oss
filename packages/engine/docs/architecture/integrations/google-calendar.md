# Google Calendar Integration

Google Calendar is the second service on the `google` OAuth provider (`packages/tools/src/services/google/calendar.ts`) — it contributes only its scopes and tools to the existing provider strategy, with no new secret or redirect URI. Its tools call the Calendar v3 REST API directly with raw `fetch` (no `googleapis` SDK), authenticated by the credential the dispatch layer resolves and injects; an executor never resolves a credential itself.

The seven tools landed as one unit: three read tools bound to a calendar, two write tools whose governed reach is the invitee list, and the two event-lifecycle verbs (cancel, RSVP).

## Tool surface

Each tool is its own `(service, verb)` permission subject with its own noun. The noun is extracted synchronously from the call's own params — no credential, no network — so it is the grant key and the audit target at once.

| Tool | Verb | Noun | Capability |
|------|------|------|-----------|
| `google_calendar_list` | `list` | the folded calendar name (trim + lowercase; defaults to `primary`) | read |
| `google_calendar_read` | `read` | the folded calendar name; the event id's value is not audited — the row records only the parameter's shape | read |
| `google_calendar_search` | `search` | the folded calendar name; the free-text `q` is never the noun, and its value is not audited — the row records only its shape | read |
| `google_calendar_create` | `create` | attendees named → the set of distinct invitee domains (lower-cased, de-duped, sorted, comma-joined; an unparseable address contributes an opaque `unparseable:<raw>` token, never dropped); attendees omitted → `calendar:<folded name>`; an empty array or non-array → the never-granted `empty-attendees` sentinel | write |
| `google_calendar_update` | `update` | `create`'s noun shape, over the update's own params | write |
| `google_calendar_cancel` | `cancel` | the folded calendar name — who a cancellation reaches lives on the *stored* event, not the call, and nouns must be knowable synchronously (the `gmail_trash` posture); the event id's value is not audited — the row records only the parameter's shape | write |
| `google_calendar_respond` | `respond` | the folded calendar name — the RSVP writes the user's own attendance and tells the organizer, one already-known party | write |

**The calendar-name noun is folded on purpose.** Calendar names are prose a user types loosely (unlike Slack's lower-case channel handles), so the client resolves them case-insensitively — and the noun must be the *same function of the input* as resolution, so governance and resolution cannot disagree on identity: `Work` and `work` produce one noun and resolve to one calendar. Resolution short-circuits `primary` (Google's built-in alias for the main calendar) with no lookup; any other name pages `calendarList.list` to exhaustion, matching each entry's *effective* display name — `summaryOverride` (the user's personal rename of a shared calendar) when present, else `summary` — under the same trim + lowercase fold. That is exactly the one name the user sees in every Google UI; a renamed calendar's hidden original title deliberately does not match. Zero matches and multiple distinct matches each throw a self-correcting error — the resolver never silently picks a first match, so the governed noun cannot bind to a calendar the user did not mean. Matches de-dupe by calendar id, because calendarList pagination is not snapshot-consistent and an entry shifting pages mid-listing would otherwise report a phantom ambiguity.

**The write verbs read one input twice.** Naming attendees *invites* them — Google emails every listed attendee — so the governed reach is the invitee-domain set and the executor sends `sendUpdates=all`. Naming none notifies no one, so the noun falls back to the calendar (prefixed `calendar:`) and the executor sends `sendUpdates=none`. Both derive from the same `attendees` param; `sendUpdates` is never agent-supplied. Each address parses through the shared fail-closed `recipientDomain` (the email-send set-noun discipline over `attendees` instead of to/cc/bcc — at domain grain today, where email send governs at address grain; alignment is planned follow-up work), and because that parser rejects colon-bearing domains, a crafted address like `x@calendar:primary` fails closed to its `unparseable:` token instead of minting the calendar prefix. With no grant the write verbs hold for confirmation on first use, and because the noun is the whole invitee-domain set, an extra domain always changes the noun and forces a fresh confirmation. Attendee addresses must be bare (`ana@example.com`): the API's `attendees[].email` field is not an RFC 5322 header, so a display-name form (`Ana <ana@example.com>`) is rejected with a self-correcting error instead of Google's opaque 400 — and fail-safe against the noun either way, since `recipientDomain` parses the display-name form to the same domain the bare address carries.

**The guest list cannot be wiped silently.** `events.patch` replaces a named array wholesale, so an absent `attendees` param never enters the patch body — the stored guest list is preserved — while a provided list replaces the whole guest list (the accepted partial-removal residual). An empty array is rejected as an input error: on `update` it would be a full guest-list wipe, too consequential to ride the calendar noun (clearing all guests is deferred).

**Cancel notifies; respond does not blast.** `google_calendar_cancel` deletes with `sendUpdates=all` — a silent cancellation strands guests at a dead slot. `google_calendar_respond` patches with `sendUpdates=none`: the RSVP is event *data* that syncs to the organizer's copy regardless; `none` only suppresses the guest-facing "event changed" notification blast.

## OAuth scopes and the capability check

`googleCalendar.connect.scopes` requests `calendar.events` + `calendar.calendarlist.readonly` (full `https://www.googleapis.com/auth/…` URLs) — the least-privilege set for read + write over events plus calendar-name resolution. The full `calendar` scope is never requested: it additionally authorizes calendar creation, sharing, and deletion, none of which the tool surface exposes. Both requested scopes are sensitive/restricted at Google — they must be on the OAuth consent screen and through verification review before external users can grant them.

The scope gate is effectively binary: the one requested event scope (`calendar.events`) carries both declared capabilities (`read` and `write`), so declining it at consent sends all seven tools to the `needs_authorization` outcome (see `docs/architecture/governance.md`), and granting it clears all seven. The capability map (`CALENDAR_CAPABILITY_SCOPES`) still covers the broader `calendar.readonly` and `calendar` scopes Habenula never requests — a credential is judged by what it holds, the posture Gmail's map takes on its umbrella scope. The name-resolution scope (`calendar.calendarlist.readonly`) is deliberately in no capability set: resolution is incidental to every verb, and a credential missing it should surface as the self-correcting "unknown calendar" tool error, not a scope denial.

**Per-service consent.** A Google consent returns a credential scoped to exactly the requested set — the begin-flow does not send `include_granted_scopes`, so connecting Calendar never inherits Gmail's scopes, and connecting Gmail never widens Calendar's stored token. Every Google connect requests its service's complete scope set; the invariant this rests on is recorded in [`footguns.md`](../../footguns.md).

**Acquiring the credential.** Registering the Google OAuth client and wiring its client ID/secret into Habenula is covered in [`connect/google.md`](../../connect/google.md).

## API quirks

- **`events.patch` replaces arrays wholesale.** Unnamed scalar fields are preserved, but a named array — `attendees` — overwrites the stored one, and any per-guest *field* the patch omits is erased with it. This drives both write-tool behaviors above (omit the key to preserve, empty array rejected) and the RSVP round-trip below.
- **There is no RSVP endpoint.** `respond` composes `events.get` + `events.patch` on the copy of the event on the user's own calendar: it sets `responseStatus` on the authenticated user's own attendee entry (the one flagged `self: true`) and patches back the full attendee list with every writable per-guest field (displayName, optional, resource, comment, additionalGuests) riding through unchanged, so no guest and no field is dropped. Read-only attendee fields stay out of the patch body; Google keys attendees by email. A user who is not on the guest list gets a self-correcting `not_an_attendee` error before any write.
- **The RSVP patch is conditional.** The read's `etag` rides the patch as `If-Match`, so a concurrent edit in the get-to-patch gap (an organizer adding a guest) fails with 412 instead of being silently reverted by the stale list. The 412 is rethrown as a self-correcting retry instruction (`event_modified`), not retried in place: a governed tool call is one audited attempt, so the retry must be a fresh call.
- **Timezone input is fail-closed.** `start`/`end` mirror Google's `EventDateTime` 1:1 — exactly one of `dateTime` (RFC 3339) or `date` (all-day, `YYYY-MM-DD`). A timed `dateTime` must carry a UTC offset or the object must set an explicit IANA `timeZone`; an offset-less, zone-less time is rejected rather than silently assumed UTC or the account's zone. Seconds are required — RFC 3339 has no seconds-less form and Google rejects one, so the input error is self-correcting where Google's 400 is opaque. An all-day `date` needs no zone.
- **`maxResults` is a per-page cap, not a result-set promise.** Google documents that a page may hold fewer events than `maxResults` — or none — even when more match; recurring-event expansion (`singleEvents=true`) makes short pages routine. The client pages `nextPageToken` until the caller's cap (default 25, max 250) is gathered, the listing is exhausted, or the page budget runs out. `truncated: true` in a result means the listing was not exhausted — never that events were silently dropped.
- **Page budgets bound the Workers subrequest spend.** Each listing loop fetches at most 10 pages — every page is a subrequest against the per-invocation platform cap. Event listing returns what it gathered, flagged truncated; name resolution instead fails whole on the budget (covering 2,500 calendars first), because a partial calendar listing could turn a real ambiguity into a wrong single match.
- **Search binds to one calendar and defaults to the future.** The current release has no cross-calendar search. A search with no time bounds injects `timeMin=now`: an unbounded `orderBy=startTime` search returns the *oldest* matches first, burying the upcoming events a bare search almost always means. A `timeMax`-only call is an explicit past search and gets no injected floor.
- **Event content never enters the audit log.** Titles, descriptions, and the attendee addresses themselves flow through for execution but are not retained; when attendees are named, what persists is the derived invitee-domain set — domains, never addresses — as the noun. Beyond `(google_calendar, verb, noun)`, the audit entry records only parameter shapes, never parameter values — the metadata-only default, exactly as email bodies are handled.
